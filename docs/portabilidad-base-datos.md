PostgreSQL es el motor **actual, conectado y probado** de la API. SQL Server es el motor principal de la empresa y tiene scripts funcionalmente equivalentes preparados, pero **SQL Server documentado/no validado contra instancia real**. No se añadió Microsoft.Data.SqlClient, EF SQL Server, instancia nueva ni proveedores runtime.

## Equivalencias

| Concepto | PostgreSQL | SQL Server |
|---|---|---|
| IDs de negocio | int GENERATED BY DEFAULT AS IDENTITY | int IDENTITY(1,1) |
| IDs catálogo Roles | int explícito, 1 Administrador / 2 Técnico | int explícito, mismos IDs |
| Fechas con offset | TIMESTAMPTZ | DATETIMEOFFSET(7) |
| Texto largo / futuro Base64 | TEXT | NVARCHAR(MAX) |
| Texto Unicode acotado | varchar(n), base UTF-8 | nvarchar(n), literales N'...' |
| Activo 0/1 | SMALLINT NOT NULL DEFAULT 1 + CHECK IN (0,1) | BIT NOT NULL DEFAULT 1 |
| Relación restrictiva | FK ON DELETE RESTRICT | FK ON DELETE NO ACTION |
| Function / SP | public.get_user_by_username(varchar), SELECT parametrizado | dbo.GetUserByUsername, parámetro/resultset |
| Connection provider actual | Conexion → Npgsql por IConexion | Sin implementar; futuro adaptador DbConnection |
| Username exacto | Comparación varchar actual | Collation BIN2 y longitud de parámetro para no igualar espacios finales |

No se cambian IDs a UUID. PostgreSQL conserva instantes normalizados; no guarda el nombre de zona original con timestamptz. SQL Server datetimeoffset puede conservar offset. La aplicación utiliza UTC para ambos motores y para la futura representación ISO-8601 en SQLite. BIT almacena dominio lógico 0/1, pero la futura API igualmente deberá validar entradas por sus reglas de conversión.

Las definiciones se revisaron contra documentación primaria: [CREATE FUNCTION PostgreSQL](https://www.postgresql.org/docs/17/sql-createfunction.html), [CREATE PROCEDURE SQL Server](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-procedure-transact-sql), [DATETIMEOFFSET](https://learn.microsoft.com/en-us/sql/t-sql/data-types/datetimeoffset-transact-sql) y [BIT](https://learn.microsoft.com/en-us/sql/t-sql/data-types/bit-transact-sql). CREATE OR ALTER PROCEDURE requiere un lote propio; GO es un separador de herramientas, no un comando de la API.

## Decisiones de esquema

- Roles es catálogo funcional normalizado con IDs estables 1 Administrador / 2 Técnico y nombre único. No implementa jerarquía de permisos.
- Users.RoleId es FK, NOT NULL, default 2. La migración completa solo valores ausentes de la línea base que tenía técnicos; conserva roles válidos ya asignados. DATOS_PRUEBA.md asigna explícitamente tecnico1 a Técnico.
- Users.IsActive es NOT NULL y default 1. La primera migración activa las cuentas antiguas; repetirla no reactiva valores 0 deliberados. Un valor inválido en una instalación personalizada aborta por constraint, no se corrige silenciosamente.
- Tickets.ScheduledAt se inicializa desde CreatedAt **solo donde falta en la migración** y después es NOT NULL. No reemplaza CreatedAt/UpdatedAt ni cambia creación al reprogramar.
- Evidences conserva CreatedAt y PhotoPath nullable. Users y Branches no tienen fechas existentes; no se añaden columnas de auditoría arbitrarias.
- Se mantienen índices existentes. No se crea un índice de agenda hasta implementar y revisar esa consulta.
- Roles base no son un usuario administrador demo; no se crea ninguna cuenta administradora.

## Runtime y autenticación

El runtime C#/Flutter de esta etapa queda sin modificaciones. Sigue compilando contra el esquema actual antes de ejecutar SQL. No se modifican Conexion, IConexion, AccesoUsuariosPostgres, DTOs, JSON, JWT, SQLite v2, Login ni Home.

Tras aplicar el esquema y la función actualizada, get_user_by_username no devuelve cuentas IsActive=0; la API conserva el 401 genérico de credenciales incorrectas sin revelar si el usuario existe/desactivado. La función mantiene las cuatro columnas actuales para no requerir DROP FUNCTION ni romper consumidores: PostgreSQL no permite alterar RETURNS TABLE con CREATE OR REPLACE.

El hash de PasswordHasher<Usuario> es de .NET, no del motor. La muestra SQL Server utiliza el mismo hash público de desarrollo que DATOS_PRUEBA.md. PasswordHash sigue reservado al acceso interno/PasswordHasher; nunca se enviará en DTOs públicos.

Después de que el usuario confirme la migración, deberá ampliarse coherentemente modelo/DTO/lectura para el rol público cuando se necesite, manteniendo compatibilidad del contrato. La sesión SQLite guardará únicamente ese rol público si lo devuelve la API; no necesita replicar Roles solo por Login. No se ha implementado aún esta ampliación.

Una cuenta desactivada después de autenticarse puede conservar sesión offline. La función bloquea nuevos logins, pero JWT emitidos anteriormente siguen válidos hasta su expiración; /me actual lee claims y no consulta IsActive. No hay revocación inmediata ni polling. Cuando una validación/sincronización futura reciba 401, ServicioSesion exige reautenticación sin borrar trabajo local. La comprobación de usuario activo al acceder a futuros endpoints debe tratarse después de aplicar la BD.

## SQLite previsto y próximo paso

La futura migración única de Tickets (prevista v2 → v3, todavía sin implementar) conservará sesión/cola y añadirá created_at, updated_at y scheduled_at como ISO-8601 UTC completos. La fecha programada no se sustituirá permanentemente por fecha actual. Cualquier ampliación de rol público se integrará cuando exista el contrato correspondiente, sin migraciones duplicadas ni catálogo offline innecesario.

La futura portabilidad utilizaría IConexion con proveedores PostgreSQL/SQL Server y IAccesoUsuarios con acceso específico por motor; los controllers seguirían ajenos a SQL. Hoy existen IConexion/Conexion e IAccesoUsuarios/AccesoUsuariosPostgres. Las implementaciones SqlServer solo se documentan como posibilidad, no se crean.

Se detiene Home Agenda, RepositorioTickets, endpoints, sincronización y evidencias hasta que el usuario ejecute ACTUALIZACION_POSTGRESQL.md manualmente y confirme resultados.
