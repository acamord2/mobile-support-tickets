# Base de datos

Este documento contiene exclusivamente la estructura física principal de PostgreSQL. Las funciones, vistas, triggers y datos demo se documentan por separado. La BD se administra fuera de la API y se instala manualmente desde pgAdmin → Query Tool. La instalación incluye el catálogo funcional Roles (1 = Administrador, 2 = Técnico, 3 = Coordinador, 4 = Usuario), sin usuarios, sucursales, tickets ni evidencias demo. Para una base existente usar ACTUALIZACION_POSTGRESQL.md; este documento ya contiene el esquema completo nuevo.

**Migraciones aplicadas localmente:** seguimiento y roles/asignación, autorizadas el 01/10/2026. Para otra base existente, usar las actualizaciones específicas en su orden. No ejecutar el instalador nuevo para migrar una base existente.

## Requisitos

- PostgreSQL instalado y ejecutándose previamente (versión disponible: 17).
- pgAdmin y un usuario con permisos para crear la base y sus objetos.
- Conexión local de desarrollo: localhost, puerto 5432, usuario postgres. La contraseña depende de la instalación y no se incluye en este documento.

## Creación de base

1. Abrir pgAdmin y conectarse al PostgreSQL local.
2. Abrir Query Tool conectado a `postgres` u otra BD administrativa.
3. Activar autocommit y ejecutar únicamente la siguiente sentencia, fuera de cualquier transacción:

```sql
CREATE DATABASE tickets_db;
```

PostgreSQL no permite CREATE DATABASE dentro de una transacción ni ofrece IF NOT EXISTS para esta sentencia. Si tickets_db ya existe, omitir este paso; no eliminar una BD existente para repetir la instalación.

4. Refrescar la lista de bases.
5. Abrir un nuevo Query Tool conectado a `tickets_db` antes de crear la estructura.

## Creación de estructura

Ejecutar el siguiente bloque completo sobre `tickets_db`. La transacción impide dejar una instalación parcial si alguna sentencia falla. Los IF NOT EXISTS permiten repetir la instalación del mismo esquema, pero no actualizan tablas incompatibles preexistentes. Si una sentencia falla, revisar el error y ejecutar ROLLBACK antes de repetir el bloque corregido.

```sql
BEGIN;

-- Roles es catálogo funcional de IDs estables, no datos demo ni permisos complejos.
CREATE TABLE IF NOT EXISTS public."Roles" (
    "Id" integer PRIMARY KEY,
    "Name" varchar(100) NOT NULL,
    CONSTRAINT "UQ_Roles_Name" UNIQUE ("Name")
);

-- Repetir el instalador no debe aceptar silenciosamente un catálogo con IDs distintos.
DO $$
BEGIN
    IF EXISTS (SELECT 1 FROM public."Roles"
        WHERE ("Id" = 1 AND "Name" <> 'Administrador')
           OR ("Id" = 2 AND "Name" <> 'Técnico')
           OR ("Id" = 3 AND "Name" <> 'Coordinador')
           OR ("Id" = 4 AND "Name" <> 'Usuario')
           OR ("Name" = 'Administrador' AND "Id" <> 1)
           OR ("Name" = 'Técnico' AND "Id" <> 2)) THEN
        RAISE EXCEPTION 'El catálogo Roles no coincide con los IDs funcionales 1/2.';
    END IF;
END;
$$;

INSERT INTO public."Roles" ("Id", "Name")
VALUES (1, 'Administrador'), (2, 'Técnico'), (3, 'Coordinador'), (4, 'Usuario')
ON CONFLICT ("Id") DO NOTHING;

CREATE TABLE IF NOT EXISTS public."Users" (
    "Id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "Username" varchar(100) NOT NULL,
    "PasswordHash" text NOT NULL,
    "Name" varchar(200) NOT NULL,
    "RoleId" integer NOT NULL DEFAULT 2,
    "IsActive" smallint NOT NULL DEFAULT 1,
    CONSTRAINT "FK_Users_Roles" FOREIGN KEY ("RoleId") REFERENCES public."Roles" ("Id") ON DELETE RESTRICT,
    CONSTRAINT "CK_Users_IsActive" CHECK ("IsActive" IN (0, 1)),
    CONSTRAINT "UQ_Users_Username" UNIQUE ("Username")
);

CREATE TABLE IF NOT EXISTS public."CoordinatorTechnicians" (
    "CoordinatorUserId" integer NOT NULL REFERENCES public."Users" ("Id") ON DELETE RESTRICT,
    "TechnicianUserId" integer NOT NULL REFERENCES public."Users" ("Id") ON DELETE RESTRICT,
    "CreatedAt" timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY ("CoordinatorUserId", "TechnicianUserId")
);
CREATE INDEX IF NOT EXISTS "IX_CoordinatorTechnicians_TechnicianUserId" ON public."CoordinatorTechnicians" ("TechnicianUserId");

CREATE TABLE IF NOT EXISTS public."Branches" (
    "Id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "Name" varchar(200) NOT NULL,
    "Address" varchar(500) NOT NULL
);

CREATE TABLE IF NOT EXISTS public."Tickets" (
    "Id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "BranchId" integer NOT NULL REFERENCES public."Branches" ("Id") ON DELETE RESTRICT,
    "TechnicianId" integer NULL REFERENCES public."Users" ("Id") ON DELETE RESTRICT,
    "ReporterUserId" integer NULL REFERENCES public."Users" ("Id") ON DELETE RESTRICT,
    "Title" varchar(200) NOT NULL,
    "Description" text NOT NULL,
    "Status" varchar(20) NOT NULL,
    "CreatedAt" timestamptz NOT NULL,
    "UpdatedAt" timestamptz NOT NULL,
    "ScheduledAt" timestamptz NOT NULL,
    "ClientRequestId" uuid NULL,
    CONSTRAINT "UQ_Tickets_ClientRequestId" UNIQUE ("ClientRequestId"),
    CONSTRAINT "CK_Tickets_Status" CHECK ("Status" IN ('Pending', 'InProgress', 'Resolved')),
    CONSTRAINT "CK_Tickets_Dates" CHECK ("UpdatedAt" >= "CreatedAt")
);

CREATE INDEX IF NOT EXISTS "IX_Tickets_ReporterUserId" ON public."Tickets" ("ReporterUserId");

CREATE INDEX IF NOT EXISTS "IX_Tickets_BranchId" ON public."Tickets" ("BranchId");
CREATE INDEX IF NOT EXISTS "IX_Tickets_TechnicianId_Status" ON public."Tickets" ("TechnicianId", "Status");

CREATE TABLE IF NOT EXISTS public."Evidences" (
    "Id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "TicketId" integer NOT NULL REFERENCES public."Tickets" ("Id") ON DELETE RESTRICT,
    "Description" text NOT NULL,
    "PhotoPath" text NULL,
    "PhotoBase64" text NULL,
    "CreatedAt" timestamptz NOT NULL,
    CONSTRAINT "UQ_Evidences_TicketId_Id" UNIQUE ("TicketId", "Id")
);

CREATE INDEX IF NOT EXISTS "IX_Evidences_TicketId" ON public."Evidences" ("TicketId");

CREATE TABLE IF NOT EXISTS public."TicketEvents" (
    "Id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "TicketId" integer NOT NULL REFERENCES public."Tickets" ("Id") ON DELETE RESTRICT,
    "EventType" varchar(20) NOT NULL,
    "Description" text NOT NULL,
    "CreatedAt" timestamptz NOT NULL,
    "UserId" integer NOT NULL REFERENCES public."Users" ("Id") ON DELETE RESTRICT,
    "ClientRequestId" uuid NOT NULL,
    "PreviousScheduledAt" timestamptz NULL,
    "ScheduledAt" timestamptz NULL,
    "EvidenceId" integer NULL,
    CONSTRAINT "UQ_TicketEvents_UserId_ClientRequestId" UNIQUE ("UserId", "ClientRequestId"),
    CONSTRAINT "FK_TicketEvents_Evidences" FOREIGN KEY ("TicketId", "EvidenceId")
        REFERENCES public."Evidences" ("TicketId", "Id") ON DELETE RESTRICT,
    CONSTRAINT "CK_TicketEvents_EventType" CHECK (
        "EventType" IN ('CREADO', 'PROGRAMADO', 'REPROGRAMADO', 'EN_ATENCION', 'SEGUIMIENTO', 'RESUELTO', 'ASIGNADO', 'REASIGNADO')),
    CONSTRAINT "CK_TicketEvents_Description" CHECK (
        length(btrim("Description")) > 0 OR ("EventType" = 'SEGUIMIENTO' AND "EvidenceId" IS NOT NULL)),
    CONSTRAINT "CK_TicketEvents_Evidence" CHECK ("EvidenceId" IS NULL OR "EventType" = 'SEGUIMIENTO'),
    CONSTRAINT "CK_TicketEvents_Schedule" CHECK (
        ("EventType" = 'PROGRAMADO' AND "PreviousScheduledAt" IS NULL AND "ScheduledAt" IS NOT NULL)
        OR ("EventType" = 'REPROGRAMADO' AND "PreviousScheduledAt" IS NOT NULL
            AND "ScheduledAt" IS NOT NULL AND "PreviousScheduledAt" <> "ScheduledAt")
        OR ("EventType" NOT IN ('PROGRAMADO', 'REPROGRAMADO')
            AND "PreviousScheduledAt" IS NULL AND "ScheduledAt" IS NULL))
);

CREATE INDEX IF NOT EXISTS "IX_TicketEvents_TicketId_CreatedAt_Id"
    ON public."TicketEvents" ("TicketId", "CreatedAt", "Id");

COMMIT;
```

### Roles

Catálogo funcional normalizado: Id int explícito (sin identity) y Name único. IDs estables: 1 = Administrador y 2 = Técnico. Son valores de referencia imprescindibles; la muestra de usuarios permanece en DATOS_PRUEBA.md. No hay tabla de permisos ni nuevos claims en esta etapa.

### Users

Campos: Id, Username, PasswordHash, Name, RoleId e IsActive. RoleId referencia Roles.Id y su default 2 corresponde a Técnico; ON DELETE RESTRICT conserva usuarios referenciados. IsActive smallint NOT NULL DEFAULT 1 acepta exclusivamente 0 (inactivo) y 1 (activo) mediante CK_Users_IsActive. Id es la PK int identity; las columnas son NOT NULL. Username es UNIQUE para identificar sin ambigüedad a un usuario. PasswordHash contendrá únicamente el hash estándar compatible con `PasswordHasher<Usuario>`; el usuario de desarrollo se prepara opcionalmente en DATOS_PRUEBA.md. No hay columna de contraseña en texto plano ni se precargan cuentas.

### Branches

Campos: Id, Name y Address. Id es la PK int identity y los datos básicos son NOT NULL. El nombre no se restringe como único porque dos sucursales podrían compartirlo; su identificador distingue cada registro.

### Tickets

Campos: Id, BranchId, TechnicianId, ReporterUserId, Title, Description, Status, CreatedAt, UpdatedAt, ScheduledAt y ClientRequestId. Id es la PK int identity; ClientRequestId, TechnicianId y ReporterUserId son nullable; los demás campos son NOT NULL. ReporterUserId preserva NULL en registros históricos desconocidos; nuevas creaciones API lo informan siempre.

- BranchId referencia Branches.Id para asegurar que la incidencia pertenece a una sucursal existente.
- TechnicianId referencia Users.Id para asegurar que el técnico asignado existe.
- ON DELETE RESTRICT evita eliminar la sucursal o el usuario mientras haya tickets que lo referencien.
- CK_Tickets_Status limita Status a Pending, InProgress y Resolved, sin introducir una tabla catálogo.
- CK_Tickets_Dates impide que UpdatedAt sea anterior a CreatedAt.
- Las fechas usan timestamptz y el código de aplicación utiliza valores UTC. CreatedAt identifica creación; UpdatedAt identifica modificación; ScheduledAt es la cita editable e independiente. No se restringe ScheduledAt >= CreatedAt: la cita puede referirse a una atención pasada. Los tickets existentes se inicializan a CreatedAt solo durante la migración.
- IX_Tickets_BranchId facilita consultas por sucursal.
- IX_Tickets_TechnicianId_Status permite localizar las incidencias asignadas y distinguir su estado.

### Evidences

Campos: Id, TicketId, Description, PhotoPath, PhotoBase64 y CreatedAt. Id es la PK int identity. TicketId referencia Tickets.Id; ON DELETE RESTRICT impide dejar evidencias sin ticket. Description y CreatedAt son NOT NULL; PhotoPath admite NULL para permitir evidencia descriptiva sin fotografía. IX_Evidences_TicketId facilita recuperar las evidencias relacionadas.

### Relaciones

```text
Roles.Id    → Users.RoleId
Branches.Id → Tickets.BranchId
Users.Id    → Tickets.TechnicianId
Tickets.Id  → Evidences.TicketId
```

Todas las relaciones permiten varios registros hijos y requieren un padre existente. Las PK y el UNIQUE de Username crean sus índices PostgreSQL correspondientes, además de los tres índices explícitos. TicketHistory no existe en la estructura aprobada y no se agrega aquí.

## Verificación manual sin datos de prueba

Después de crear una base nueva con los bloques anteriores, estas consultas de lectura permiten comprobar las tablas, las referencias de Roles y que las tablas de negocio están vacías:

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public' AND table_type = 'BASE TABLE'
ORDER BY table_name;

SELECT 'Roles' AS table_name, count(*) AS rows FROM public."Roles"
UNION ALL SELECT 'Users', count(*) AS rows FROM public."Users"
UNION ALL SELECT 'Branches', count(*) FROM public."Branches"
UNION ALL SELECT 'Tickets', count(*) FROM public."Tickets"
UNION ALL SELECT 'Evidences', count(*) FROM public."Evidences";
```

El resultado esperado en una instalación nueva con la propuesta aprobada es siete tablas: Roles contiene cuatro referencias funcionales y Users, Branches, Tickets, Evidences y TicketEvents tienen cero filas. Este documento no borra datos que ya existan en una instalación anterior y no ejecuta SQL automáticamente. La API tampoco crea, migra ni repara la BD; solo se conecta cuando una operación necesita acceder a los datos.

## Evolución controlada y fechas

Users y Branches no tienen campos temporales en el esquema actual; no se añaden fechas de auditoría sin requisito. Evidences conserva CreatedAt y PhotoPath TEXT nullable. PhotoBase64 TEXT nullable está autorizado para contenido Base64 completo sin prefijo; PhotoPath se conserva. El procesamiento y la sincronización todavía no están implementados. Tickets conserva ScheduledAt y añade ClientRequestId nullable para idempotencia móvil. La restricción nueva de unicidad crea su índice; el índice existente por técnico/estado continúa válido; el índice de agenda se evaluará al implementar y medir su consulta.

Para la base ya instalada ejecutar manualmente ACTUALIZACION_POSTGRESQL.md, con la función canónica de FUNCIONES_SP.md dentro de la misma transacción según sus instrucciones. No ejecutar este instalador para intentar migrar: IF NOT EXISTS no altera tablas antiguas. ## Idempotencia móvil y fotografía autorizadas

ClientRequestId UUID nullable identifica una creación móvil y no sustituye Tickets.Id int. Se generará una sola vez en el dispositivo y se conservará en SQLite en todos los reintentos. UQ_Tickets_ClientRequestId protege la clave global frente a concurrencia, sin depender del técnico mutable; la futura API recuperará el mismo ticket ante conflicto. PostgreSQL permite varios NULL para un técnico con esta restricción, conservando tickets antiguos sin clave. No se generan ni rellenan claves en el instalador.

PhotoBase64 TEXT nullable conserva el contenido Base64 íntegro, sin prefijo data:. PhotoPath permanece disponible. La futura aplicación producirá JPEG, reducirá dimensiones y comprimirá antes de codificar; la API validará como máximo 1 MB de bytes decodificados y nunca truncará el contenido. No se añade una columna MIME en esta etapa: la implementación futura deberá fijar y validar el formato admitido.

Para la base existente ya migrada aplicar manualmente ACTUALIZACION_TICKETS_POSTGRESQL.md. Este instalador nuevo incluye ambas columnas y la restricción directamente. Ningún SQL de esta etapa se ejecutó; no hay cambios runtime ni nuevos objetos de agenda hasta la confirmación manual.

Referencias: [unicidad PostgreSQL y NULL](https://www.postgresql.org/docs/17/ddl-constraints.html), [índices filtrados SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/create-filtered-indexes).


## TicketEvents — seguimiento y asignación implementados

Tickets conserva únicamente CreatedAt, UpdatedAt, ScheduledAt y Status actuales: no guarda cuándo cambió cada valor ni la programación anterior. Evidences conserva texto/foto/fecha, pero carece de tipo de evento y autor responsable. La cola es técnica, no un historial: sus payloads actuales referencian registros mutables y no contienen una instantánea de cada acción. Los modelos/DTOs/endpoints actuales no transportan eventos. La revisión se realizó sobre las definiciones documentadas y el código; no se ejecutaron consultas SQL ni se verificó esta propuesta contra una instancia.

TicketEvents tiene Id, TicketId, EventType, Description, CreatedAt, UserId, ClientRequestId, PreviousScheduledAt, ScheduledAt y EvidenceId. CreatedAt representa el instante original del evento, UTC, incluso offline; nunca la hora de sincronización. UserId conserva identidad del responsable, independiente del nombre actual de sesión. No se añade un snapshot del nombre: puede resolverse públicamente por Id, manteniendo trazabilidad aunque cambie el nombre del usuario. La FK restrictiva impide eliminar al responsable referenciado.

Los seis tipos exactos son CREADO, PROGRAMADO, REPROGRAMADO, EN_ATENCION, SEGUIMIENTO y RESUELTO. Enums en Dart/C# centralizan su serialización. PROGRAMADO conserva la cita inicial; REPROGRAMADO guarda cita anterior/nueva distintas. Los demás no necesitan datos de programación. Orden: CreatedAt, Id. No generar eventos por UpdatedAt, confirmación remota o intentos de cola.

Ticket → muchos TicketEvents. Cada evento SEGUIMIENTO puede referenciar una Evidence opcional del mismo Ticket mediante la FK compuesta (TicketId, EvidenceId); la clave UNIQUE (TicketId, Id) de Evidences permite esa referencia. La foto/Base64 continúa exclusivamente en Evidences. No se impone unicidad de EvidenceId en eventos: una evidencia deduplicada puede ser referenciada por eventos distintos, sin duplicar imagen. Los eventos automáticos nunca usan EvidenceId.

Manual: texto sin fotografía es válido. Texto con foto es válido. Solo foto también es válido si contiene una imagen real y válida; Description puede ser cadena vacía únicamente en SEGUIMIENTO con EvidenceId. Sin texto ni foto se rechaza. La API comprueba contenido, límite JPEG existente de 1 MiB, pertenencia del ticket y UserId derivado del JWT; una FK no sustituye esas validaciones. Evidences.Description existente se conserva compatible para su leyenda; no se reutiliza como contenedor de eventos automáticos.

Previsualización: seleccionar/capturar → ServicioImagen → JPEG comprimido → Image.memory del Base64 resultante → revisar/reemplazar/quitar → Guardar. Quitar solo modifica el borrador; no elimina evidencias persistidas. No guardar antes de confirmación del formulario. La vista temporal muestra exactamente los bytes que finalmente se almacenan.

### SQLite y sincronización implementadas

Migración aditiva v3 → v4: tabla ticket_eventos con id_local, id_remoto nullable, ticket_id_local, usuario_id (propietario), autor_id, usuario_nombre, tipo_evento, descripcion, created_at UTC ISO-8601, client_request_id UUID obligatorio, scheduled_at/previous_scheduled_at opcionales, evidencia_id_local opcional y sync_status synced/pending. FK hacia tickets/evidencias locales; el repositorio verifica mismo ticket y propietario. Índices únicos por usuario/UUID y por usuario/Id remoto no nulo, más índice de lectura por usuario/ticket/fecha/Id local. No borrar sesión, tickets, evidencias ni cola existentes. No generar retrospectivamente eventos ni asumir que TechnicianId prueba autoría histórica.

Una transacción local guarda acción de negocio, eventos inmutables y operaciones de la cola existente. Crear: CREADO + PROGRAMADO con cita inicial; reprogramar: REPROGRAMADO con ambos valores; iniciar/resolver: EN_ATENCION/RESUELTO. Manual: SEGUIMIENTO y evidencia opcional juntos. Cada UUID nace una sola vez; payload de cola referencia el evento local, cuyo contenido ya es una instantánea de la acción, no el último estado mutable del ticket. Las acciones de UI no ofrecen escribir tipos automáticos.

ServicioSincronizacion se amplía dentro de su ciclo actual para el recurso eventos, sin otro sincronizador: ticket remoto confirmado → evidencia opcional confirmada → evento con sus referencias remotas. Si falta una dependencia, la operación permanece pendiente. La API acepta los UUID y la fecha original, mantener idempotencia por (UserId, ClientRequestId), validar tipos/autoría y devolver eventos para caché local. POST y GET /api/tickets/{id}/events amplían el contrato existente. Los tipos automáticos viajarán vinculados a las acciones de negocio y sus UUID; el formulario manual solicita solamente SEGUIMIENTO. Cada evento se persistirá atómicamente con su clave de reintento en servidor; las operaciones de negocio y eventos seguirán pendientes hasta sus respectivas confirmaciones. La API no deberá generar además otra copia del evento al recibir PUT: persistirá la instantánea inmutable enviada, sin reconstruirla del último estado mutable. Descargas reconciliarán UUID/Id remoto, respetarán pending y mantendrán orden cronológico.

Los eventos anteriores que nunca se guardaron no pueden recuperarse con veracidad. Las evidencias históricas se conservan como datos existentes; no se inventa su usuario, hora de inicio/resolución ni reprogramaciones. La migración autorizada fue aplicada en PostgreSQL local el 01/10/2026; SQLite v4 y el runtime utilizan esta estructura. SQL Server no se ejecutó.

## Roles y asignación

La migración ACTUALIZACION_ROLES_ASIGNACION_POSTGRESQL.md fue aplicada el 01/10/2026 después de confirmar cero UUID duplicados. Conservar reportantes históricos desconocidos como NULL evita atribuciones falsas. La API deriva ReporterUserId de la identidad al crear, utiliza NULL real para técnico sin asignar y mantiene ClientRequestId estable al asignar/reasignar.

CoordinatorTechnicians representa únicamente coordinadores y técnicos relacionados. La API comprueba roles/actividad; el administrador consulta globalmente sin relación artificial. Un coordinador ve el conjunto común de tickets sin asignar y los de su equipo; no hay tenant/sucursal de coordinación en este modelo y no se inventa ese alcance. La relación tiene PK compuesta y FK restrictivas.

ASIGNADO y REASIGNADO conservan en Description nombres e IDs de técnicos anterior/nuevo; UserId conserva al responsable. No se agrega historia editable ni columnas adicionales al evento. SQL Server sigue únicamente documentado.
