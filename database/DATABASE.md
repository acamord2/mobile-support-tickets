# Base de datos

Este documento contiene exclusivamente la estructura física principal de PostgreSQL. Las funciones, vistas, triggers y datos demo se documentan por separado. La BD se administra fuera de la API y se instala manualmente desde pgAdmin → Query Tool. La instalación incluye el catálogo funcional Roles (1 = Administrador, 2 = Técnico), sin usuarios, sucursales, tickets ni evidencias demo. Para una base existente usar ACTUALIZACION_POSTGRESQL.md; este documento ya contiene el esquema completo nuevo.

## Requisitos

- PostgreSQL instalado y ejecutándose previamente (versión disponible: 17).
- pgAdmin y un usuario con permisos para crear la base y sus objetos.
- Conexión local de desarrollo: localhost, puerto 5432, usuario postgres. La contraseña depende de la instalación y no se incluye en este documento.

## Creación de base

1. Abrir pgAdmin y conectarse al PostgreSQL local.
2. Abrir Query Tool conectado a `postgres` u otra BD administrativa.
3. Activar autocommit y ejecutar únicamente la siguiente sentencia, fuera de cualquier transacción:

```sql
CREATE DATABASE tickets_db;
```

PostgreSQL no permite CREATE DATABASE dentro de una transacción ni ofrece IF NOT EXISTS para esta sentencia. Si tickets_db ya existe, omitir este paso; no eliminar una BD existente para repetir la instalación.

4. Refrescar la lista de bases.
5. Abrir un nuevo Query Tool conectado a `tickets_db` antes de crear la estructura.

## Creación de estructura

Ejecutar el siguiente bloque completo sobre `tickets_db`. La transacción impide dejar una instalación parcial si alguna sentencia falla. Los IF NOT EXISTS permiten repetir la instalación del mismo esquema, pero no actualizan tablas incompatibles preexistentes. Si una sentencia falla, revisar el error y ejecutar ROLLBACK antes de repetir el bloque corregido.

```sql
BEGIN;

-- Roles es catálogo funcional de IDs estables, no datos demo ni permisos complejos.
CREATE TABLE IF NOT EXISTS public."Roles" (
    "Id" integer PRIMARY KEY,
    "Name" varchar(100) NOT NULL,
    CONSTRAINT "UQ_Roles_Name" UNIQUE ("Name")
);

-- Repetir el instalador no debe aceptar silenciosamente un catálogo con IDs distintos.
DO $$
BEGIN
    IF EXISTS (SELECT 1 FROM public."Roles"
        WHERE ("Id" = 1 AND "Name" <> 'Administrador')
           OR ("Id" = 2 AND "Name" <> 'Técnico')
           OR ("Name" = 'Administrador' AND "Id" <> 1)
           OR ("Name" = 'Técnico' AND "Id" <> 2)) THEN
        RAISE EXCEPTION 'El catálogo Roles no coincide con los IDs funcionales 1/2.';
    END IF;
END;
$$;

INSERT INTO public."Roles" ("Id", "Name")
VALUES (1, 'Administrador'), (2, 'Técnico')
ON CONFLICT ("Id") DO NOTHING;

CREATE TABLE IF NOT EXISTS public."Users" (
    "Id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "Username" varchar(100) NOT NULL,
    "PasswordHash" text NOT NULL,
    "Name" varchar(200) NOT NULL,
    "RoleId" integer NOT NULL DEFAULT 2,
    "IsActive" smallint NOT NULL DEFAULT 1,
    CONSTRAINT "FK_Users_Roles" FOREIGN KEY ("RoleId") REFERENCES public."Roles" ("Id") ON DELETE RESTRICT,
    CONSTRAINT "CK_Users_IsActive" CHECK ("IsActive" IN (0, 1)),
    CONSTRAINT "UQ_Users_Username" UNIQUE ("Username")
);

CREATE TABLE IF NOT EXISTS public."Branches" (
    "Id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "Name" varchar(200) NOT NULL,
    "Address" varchar(500) NOT NULL
);

CREATE TABLE IF NOT EXISTS public."Tickets" (
    "Id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "BranchId" integer NOT NULL REFERENCES public."Branches" ("Id") ON DELETE RESTRICT,
    "TechnicianId" integer NOT NULL REFERENCES public."Users" ("Id") ON DELETE RESTRICT,
    "Title" varchar(200) NOT NULL,
    "Description" text NOT NULL,
    "Status" varchar(20) NOT NULL,
    "CreatedAt" timestamptz NOT NULL,
    "UpdatedAt" timestamptz NOT NULL,
    "ScheduledAt" timestamptz NOT NULL,
    CONSTRAINT "CK_Tickets_Status" CHECK ("Status" IN ('Pending', 'InProgress', 'Resolved')),
    CONSTRAINT "CK_Tickets_Dates" CHECK ("UpdatedAt" >= "CreatedAt")
);

CREATE INDEX IF NOT EXISTS "IX_Tickets_BranchId" ON public."Tickets" ("BranchId");
CREATE INDEX IF NOT EXISTS "IX_Tickets_TechnicianId_Status" ON public."Tickets" ("TechnicianId", "Status");

CREATE TABLE IF NOT EXISTS public."Evidences" (
    "Id" integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "TicketId" integer NOT NULL REFERENCES public."Tickets" ("Id") ON DELETE RESTRICT,
    "Description" text NOT NULL,
    "PhotoPath" text NULL,
    "CreatedAt" timestamptz NOT NULL
);

CREATE INDEX IF NOT EXISTS "IX_Evidences_TicketId" ON public."Evidences" ("TicketId");

COMMIT;
```

### Roles

Catálogo funcional normalizado: Id int explícito (sin identity) y Name único. IDs estables: 1 = Administrador y 2 = Técnico. Son valores de referencia imprescindibles; la muestra de usuarios permanece en DATOS_PRUEBA.md. No hay tabla de permisos ni nuevos claims en esta etapa.

### Users

Campos: Id, Username, PasswordHash, Name, RoleId e IsActive. RoleId referencia Roles.Id y su default 2 corresponde a Técnico; ON DELETE RESTRICT conserva usuarios referenciados. IsActive smallint NOT NULL DEFAULT 1 acepta exclusivamente 0 (inactivo) y 1 (activo) mediante CK_Users_IsActive. Id es la PK int identity; las columnas son NOT NULL. Username es UNIQUE para identificar sin ambigüedad a un usuario. PasswordHash contendrá únicamente el hash estándar compatible con `PasswordHasher<Usuario>`; el usuario de desarrollo se prepara opcionalmente en DATOS_PRUEBA.md. No hay columna de contraseña en texto plano ni se precargan cuentas.

### Branches

Campos: Id, Name y Address. Id es la PK int identity y los datos básicos son NOT NULL. El nombre no se restringe como único porque dos sucursales podrían compartirlo; su identificador distingue cada registro.

### Tickets

Campos: Id, BranchId, TechnicianId, Title, Description, Status, CreatedAt, UpdatedAt y ScheduledAt. Id es la PK int identity; todos los campos son NOT NULL.

- BranchId referencia Branches.Id para asegurar que la incidencia pertenece a una sucursal existente.
- TechnicianId referencia Users.Id para asegurar que el técnico asignado existe.
- ON DELETE RESTRICT evita eliminar la sucursal o el usuario mientras haya tickets que lo referencien.
- CK_Tickets_Status limita Status a Pending, InProgress y Resolved, sin introducir una tabla catálogo.
- CK_Tickets_Dates impide que UpdatedAt sea anterior a CreatedAt.
- Las fechas usan timestamptz y el código de aplicación utiliza valores UTC. CreatedAt identifica creación; UpdatedAt identifica modificación; ScheduledAt es la cita editable e independiente. No se restringe ScheduledAt >= CreatedAt: la cita puede referirse a una atención pasada. Los tickets existentes se inicializan a CreatedAt solo durante la migración.
- IX_Tickets_BranchId facilita consultas por sucursal.
- IX_Tickets_TechnicianId_Status permite localizar las incidencias asignadas y distinguir su estado.

### Evidences

Campos: Id, TicketId, Description, PhotoPath y CreatedAt. Id es la PK int identity. TicketId referencia Tickets.Id; ON DELETE RESTRICT impide dejar evidencias sin ticket. Description y CreatedAt son NOT NULL; PhotoPath admite NULL para permitir evidencia descriptiva sin fotografía. IX_Evidences_TicketId facilita recuperar las evidencias relacionadas.

### Relaciones

```text
Roles.Id    → Users.RoleId
Branches.Id → Tickets.BranchId
Users.Id    → Tickets.TechnicianId
Tickets.Id  → Evidences.TicketId
```

Todas las relaciones permiten varios registros hijos y requieren un padre existente. Las PK y el UNIQUE de Username crean sus índices PostgreSQL correspondientes, además de los tres índices explícitos. TicketHistory no existe en la estructura aprobada y no se agrega aquí.

## Verificación manual sin datos de prueba

Después de crear una base nueva con los bloques anteriores, estas consultas de lectura permiten comprobar las tablas, las referencias de Roles y que las tablas de negocio están vacías:

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public' AND table_type = 'BASE TABLE'
ORDER BY table_name;

SELECT 'Roles' AS table_name, count(*) AS rows FROM public."Roles"
UNION ALL SELECT 'Users', count(*) AS rows FROM public."Users"
UNION ALL SELECT 'Branches', count(*) FROM public."Branches"
UNION ALL SELECT 'Tickets', count(*) FROM public."Tickets"
UNION ALL SELECT 'Evidences', count(*) FROM public."Evidences";
```

El resultado esperado en una instalación nueva es cinco tablas: Roles contiene dos referencias funcionales y Users, Branches, Tickets y Evidences tienen cero filas. Este documento no borra datos que ya existan en una instalación anterior y no ejecuta SQL automáticamente. La API tampoco crea, migra ni repara la BD; solo se conecta cuando una operación necesita acceder a los datos.

## Configuración de la API

Configurar ConnectionStrings:DefaultConnection mediante .NET User Secrets en desarrollo, siguiendo README.md. No guardar la contraseña en appsettings versionados. Linux utilizaría la variable de entorno ConnectionStrings__DefaultConnection. La API no ejecuta archivos SQL de instalación, no crea estructura y no inserta datos demo.

Después de este documento, continuar con FUNCIONES_SP.md, VISTAS.md y TRIGGERS.md. DATOS_PRUEBA.md es opcional y exclusivo de desarrollo. Las verificaciones de cero filas se refieren a una instalación nueva sin datos demo.

## Evolución controlada y fechas

Users y Branches no tienen campos temporales en el esquema actual; no se añaden fechas de auditoría sin requisito. Evidences conserva CreatedAt y PhotoPath TEXT nullable. No se implementa Base64 ni se modifica evidencia en esta etapa. Tickets añade solo ScheduledAt. No hay índices nuevos: el índice existente por técnico/estado continúa válido; el índice de agenda se evaluará al implementar y medir su consulta.

Para la base ya instalada ejecutar manualmente ACTUALIZACION_POSTGRESQL.md, con la función canónica de FUNCIONES_SP.md dentro de la misma transacción según sus instrucciones. No ejecutar este instalador para intentar migrar: IF NOT EXISTS no altera tablas antiguas. La API sigue usando el esquema anterior hasta que el usuario confirme la aplicación de SQL; no instala ninguno de estos documentos.
